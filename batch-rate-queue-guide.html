1 The Core Problem: The Dual-Bottleneck Dilemma

Modern backend microservices ingest high-velocity events, call rate-limited third-party APIs (OpenAI, Stripe, Shopify, Google Maps), and persist state back into relational databases. This inevitably crashes production under two opposing bottlenecks:

Bottleneck A: Downstream API 429 Throttle

External APIs enforce rigid rate limits (e.g., 50 req/sec). Uncoordinated parallel workers burst past limits, generating cascades of HTTP 429 errors and service bans.

Bottleneck B: Database Connection Exhaustion (N+1 Writes)

Writing every job result individually produces 1,000 single SQL UPDATE queries/sec, exhausting DB connection pools, triggering row-lock contention, and spiking CPU.

4 Step-by-Step Setup: Core Pipeline & Quickstart

Follow these steps to configure batch-rate-queue in any TypeScript / Node.js backend. Zero infrastructure required.

STEP 1 Install Package
Zero external runtime dependencies. Works with npm, pnpm, or yarn.
Terminalbash
# Install pure TypeScript package
npm install batch-rate-queue

# Optional peer dependency for Postgres
npm install pg @types/pg
STEP 2 Import & Define Job Data Interfaces
Strongly-typed data structures for job inputs and flush outputs.
types.tstypescript
import { BatchRateQueue } from "batch-rate-queue";

interface GeocodeInput {
  id: string;
  address: string;
  userId: string;
}

interface GeocodeResult {
  id: string;
  lat: number;
  lng: number;
  status: "SUCCESS" | "FAILED";
}
STEP 3 Initialize Queue with Rate Limiting & Write Buffering
Combine the token bucket (50 req/sec) and micro-batch buffer (flush every 50 items or 2,000ms, whichever happens first).
queue-init.tstypescript
const queue = new BatchRateQueue<GeocodeInput, GeocodeResult>({
  // 1. Token-Bucket Rate Limiter (Downstream Protection)
  rateLimit: {
    maxRequests: 50,      // 50 requests allowed per window
    windowMs: 1000,       // 1 second window (50 RPS)
    burstLimit: 65,       // Allow short spikes up to 65 requests
    concurrency: 10       // Max 10 parallel active workers
  },

  // 2. Micro-Batched SQL Write Buffer (Database Protection)
  batchSize: 50,          // Trigger immediate DB write when buffer hits 50 items
  flushIntervalMs: 2000,  // Time-based flush safety net every 2 seconds
  isolateBatchFailures: true, // Salvage valid writes if one item fails DB constraint

  // 3. Worker Function: Executes single job (Rate-limited)
  worker: async (job) => {
    const res = await fetch(`https://api.geocoding.com/v1?q=${encodeURIComponent(job.data.address)}`);
    
    // Record live provider headers to auto-adapt cooldowns on rate spikes
    queue.recordResponseHeaders(Object.fromEntries(res.headers.entries()));
    const json = await res.json();

    return { id: job.id, lat: json.lat, lng: json.lng, status: "SUCCESS" };
  },

  // 4. Flush Handler: Writes entire batch in 1 single SQL operation
  flush: async (batch) => {
    await pool.query(
      `INSERT INTO geocodes (id, lat, lng, status)
       SELECT * FROM jsonb_to_recordset($1::jsonb) AS x(id text, lat numeric, lng numeric, status text)
       ON CONFLICT (id) DO UPDATE SET lat = EXCLUDED.lat, lng = EXCLUDED.lng, status = EXCLUDED.status`,
      [JSON.stringify(batch)]
    );
  }
});
STEP 4 Enqueue Jobs with Priority
Push single or bulk jobs with customizable priority levels.
enqueue.tstypescript
// Push individual job
await queue.push({
  id: "job_01",
  data: { id: "loc_01", address: "1 Market St, SF", userId: "usr_99" },
  priority: 10 // High priority executes first
});

// Bulk push 10,000 jobs instantaneously
await queue.pushMany(itemsList);
STEP 5 Listen to Lifecycle Events
Observability hooks for metrics, logging, and alerts.
events.tstypescript
queue.on("job:success", ({ job, durationMs }) => {
  metrics.histogram("job_latency_ms", durationMs);
});

queue.on("buffer:flush", ({ count, durationMs }) => {
  console.log(`Flushed ${count} rows in ${durationMs}ms`);
});

queue.on("drain", () => console.log("All tasks complete!"));

5 Step-by-Step Setup: Enterprise & Resiliency Features

Configure the enterprise capabilities introduced in v1.4.0 to eliminate real-world distributed edge-case failures.

STEP 6 Side-Effect Idempotency
Prevents duplicate external calls (Stripe charges) if workers crash before DB write.
idempotency.tstypescript
import { BatchRateQueue, MemoryIdempotencyStore } from "batch-rate-queue";

const queue = new BatchRateQueue({
  // Enable idempotency tracking with TTL
  idempotency: {
    enabled: true,
    ttlMs: 86400000, // 24 hours
    store: new MemoryIdempotencyStore() // or custom Postgres
  },
  worker: async (job) => {
    // Automatically skipped if already executed!
    return await stripe.charges.create(job.data);
  }
});
STEP 7 Partial Batch Isolation
Prevents 1 constraint error from discarding 49 good writes.
partial-batch.tstypescript
const queue = new BatchRateQueue({
  batchSize: 50,
  isolateBatchFailures: true, // Enabled by default!
  flush: async (batch) => {
    // If bulk insert throws a constraint violation,
    // queue automatically falls back to salvage mode,
    // saving 49 valid rows & isolating 1 bad row.
    await db.records.createMany({ data: batch });
  }
});
STEP 8 PgBouncer-Safe Lease Locks
100% safe on Supabase, Neon & RDS Proxy transaction pooling.

import { PgLeaseLock } from "batch-rate-queue/distributed/pg-lease-lock";

const lease = new PgLeaseLock({

STEP 9 Claim-Check for Heavy Payloads
Offloads large data (>64KB) to keep DB scans fast.

const claimCheck = new ClaimCheckManager({

// Offloads 10MB payload to S3; returns 120B pointer

Deficit Round Robin ensures 1 tenant never starves others.

Zero data loss during Kubernetes pod rollouts & deployments.

6 Production Database Adapters & High-Throughput Bulk Patterns

Standard ORM calls (prisma.user.update()) in loops kill performance. Use these battle-tested bulk patterns to achieve 10,000+ writes/sec with minimal DB connection overhead:

PostgreSQL: Parameterized UNNEST / JSONB (Max Throughput)

Serializes 50 objects into 1 parameterized JSON array. Executes in a single database roundtrip with zero string concatenation.

pg-flush.tstypescript
import { Pool } from "pg";
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

const flush = async (batch: ResultItem[]) => {
  const sql = `
    INSERT INTO user_enrichments (user_id, email, score, updated_at)
    SELECT 
      x.user_id, x.email, x.score, NOW()
    FROM jsonb_to_recordset($1::jsonb) AS x(
      user_id text, 
      email text, 
      score numeric
    )
    ON CONFLICT (user_id) DO UPDATE 
    SET score = EXCLUDED.score, updated_at = EXCLUDED.updated_at;
  `;
  await pool.query(sql, [JSON.stringify(batch)]);
};

Prisma ORM: Multi-Entity Batch Transactions

Uses Prisma $transaction and createMany to insert chunks within a single connection acquisition.

prisma-flush.tstypescript
import { PrismaClient } from "@prisma/client";
const prisma = new PrismaClient();

const flush = async (batch: ResultItem[]) => {
  await prisma.$transaction([
    // 1. Bulk insert audit log rows
    prisma.auditLog.createMany({
      data: batch.map(b => ({ id: b.id, action: b.action, status: "DONE" })),
      skipDuplicates: true
    }),
    // 2. Update parent status in single query
    prisma.batchSummary.updateMany({
      where: { id: { in: batch.map(b => b.summaryId) } },
      data: { processedCount: { increment: batch.length } }
    })
  ]);
};

SQLite: WAL-Mode Bulk Prepared Statements

Wraps 50 prepared statement iterations inside a single SQLite transaction, boosting write speed from 60 writes/sec to 15,000+ writes/sec.

sqlite-flush.tstypescript
import Database from "better-sqlite3";
const db = new Database("data.db");
db.pragma("journal_mode = WAL");

const insertStmt = db.prepare(
  "INSERT OR REPLACE INTO metrics (id, val, ts) VALUES (?, ?, ?)"
);

const flushTx = db.transaction((batch: MetricItem[]) => {
  for (const item of batch) {
    insertStmt.run(item.id, item.val, Date.now());
  }
});

const flush = async (batch) => flushTx(batch);

Circuit Breaker State Machine & Dead-Letter Queue (DLQ) Integration

When an external provider fails with consecutive 500/503 errors, batch-rate-queue automatically transitions through CLOSED → OPEN (fail-fast without network calls) → HALF-OPEN (trial request probe). Exhausted retries are cleanly routed to a dead-letter queue table for manual triage.

7 Deep-Dive: Mathematical Models & Core Algorithms

Underneath the clean API surface lies a deterministic distributed coordination and fair scheduling engine:

1. Deficit Round Robin (DRR) Fair Scheduling

Each tenant receives a deficit counter allocated by quantum $Q_i$. When a tenant's turn arrives, the scheduler consumes tokens proportional to task cost $C$:

Deficit[i] = Deficit[i] + Quantum[i];
while (Queue[i].length > 0 && Cost(Task) <= Deficit[i]) {
  Deficit[i] -= Cost(Task);
  dispatch(Task);
}

2. Token Bucket with Sub-Millisecond Refill Math

Tokens are lazily recalculated on consumption without running continuous timer intervals, preventing CPU wakeups:

Δt = (Now - LastRefillTime);
NewTokens = min(Capacity, CurrentTokens + Δt * Rate);
if (NewTokens >= RequiredCost) {
  CurrentTokens = NewTokens - RequiredCost;
  return ALLOWED;
}

9 Partial Batch Failure Salvage State Machine

Phase 1: Fast Path Bulk Flush

Executes 50 items in a single bulk transaction. If successful, completes in 1ms with 0 overhead.

Phase 2: Error Classification

Detects constraint violations vs network disconnects. Transient errors trigger batch retry.

Phase 3: Item-by-Item Salvage

Saves 49 valid writes individually, isolates and logs the 1 bad record without losing progress.

11 Production Hardening Checklist

  • ✓ Connection Pool Sizing: Sized for peak concurrent flush workers (e.g. max: 10).
  • ✓ Database Indexes: Unique indexes created on idempotency keys and target conflict columns.
  • ✓ Memory Budget: Sized queue length limit (e.g. maxQueueSize: 50000) to bound RAM.
  • ✓ Graceful Shutdown: Registered setupGracefulShutdown() on SIGTERM/SIGINT.
  • ✓ PgBouncer Check: Using PgLeaseLock for distributed locks in transaction pooling mode.
  • ✓ Payload Threshold: Enabled claim-check for payloads >64KB to prevent page table bloat.
  • ✓ Dead-Letter Alerts: Attached listener to job:failed to alert on retry exhaustion.
  • ✓ Prometheus Metrics: Exported queue.getStats() to Grafana / Datadog dashboards.
